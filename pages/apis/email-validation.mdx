# Email Validation API

Check an address at signup, before it reaches your database. One call tells you
whether the address is well formed, whether its domain can receive mail, whether
it belongs to a disposable inbox service, whether it's a role account like
`support@`, and whether it looks like a typo of a common provider.

- **Disposable detection** uses the community-maintained
  [disposable-email-domains](https://github.com/disposable-email-domains/disposable-email-domains)
  list (more than 10,000 domains, refreshed weekly) and matches subdomains too:
  `inbox.mailinator.com` is flagged like `mailinator.com`.
- **Typo suggestions** catch one-character mistakes in common providers:
  `gmail.con`, `yaho.com`, `outlok.com`. Real providers that happen to look
  similar, such as `mail.com` and `ymail.com`, are never "corrected".

Costs 1 unit per call, on every plan including Free.

## Endpoint

```http
POST https://api.apimask.dev/v1/utility/email/validate
```

`POST /v1/dev/email/validate` is the same endpoint under the developer utilities
path. Both return the same response.

## Request body

| Field | Type | Required | Description |
|---|---|---:|---|
| `email` | `string` | Yes | The address to check. |
| `check_smtp` | `boolean` | No | Accepted for compatibility. Mailbox probing is not available on the hosted API, so `smtp_verified` is always `false`. |

## Example request

```bash
curl --request POST \
  --url https://api.apimask.dev/v1/utility/email/validate \
  --header "Authorization: Bearer $APIMASK_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{"email":"jane@gmail.con"}'
```

## Response fields

| Field | Type | Description |
|---|---|---|
| `is_valid` | `boolean` | Whether the address is **syntactically** valid. It does not mean the domain accepts mail; check `has_mx_records` for that. |
| `email` | `string` or `null` | The normalized address, or `null` when invalid. |
| `local_part` | `string` or `null` | The part before `@`. |
| `domain` | `string` or `null` | The part after `@`. |
| `is_disposable` | `boolean` | Whether the domain, or a parent domain, is a known disposable inbox service. |
| `has_mx_records` | `boolean` | Whether the domain publishes MX records, meaning it is set up to receive mail. |
| `smtp_verified` | `boolean` | Always `false` on the hosted API. See [Limitations](#limitations). |
| `is_role_account` | `boolean` | Whether the local part is a role such as `support`, `info`, or `admin`. |
| `reason` | `string` or `null` | Why the address is invalid, in a sentence you can show the user. `null` when valid. |
| `did_you_mean` | `string` or `null` | A corrected address when the domain looks like a typo of a common provider. The local part is kept as typed. `null` when there is no suggestion. |

## Using it at signup

A reasonable policy for a signup form:

1. `is_valid` is `false`: reject, and show `reason`.
2. `did_you_mean` is set: ask "Did you mean jane@gmail.com?" and let the user
   accept or keep what they typed. Don't change the address silently.
3. `is_disposable` is `true`: reject, or allow and flag the account for review.
4. `has_mx_records` is `false`: the address can't receive mail; reject or ask
   again.
5. `is_role_account` is `true`: usually fine for B2B products, worth a flag for
   free trials.

Call it from your server, not the browser, so the API key stays private.

## Limitations

- **No mailbox verification.** The hosted API can't open SMTP connections, so it
  can't tell whether `jane@` exists at a real domain. It checks the domain, not
  the mailbox. For cleaning old marketing lists where bounces are the main
  concern, a service that verifies mailboxes is a better fit.
- **Disposable lists are never complete.** New throwaway domains appear daily.
  The list is refreshed weekly, and a domain that was registered yesterday may
  not be on it yet.
- **Suggestions cover common providers only** (Gmail, Yahoo, Outlook, iCloud, and
  about 20 others). A typo in a company domain won't get a suggestion.
